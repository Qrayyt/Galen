## Обязательный этап: форматирование ответов и исправление склеивания слов

### Причина

Текущий `ReactMarkdown + remark-gfm` умеет базовый Markdown, но этого недостаточно для законченного интерфейса. Найдена конкретная причина склеек в самом Galen: App.tsx на каждом событии token повторно использовал результат visibleAnswer(), а splitReasoningText() вызывает trim(). Завершающий пробел/перенос предыдущего фрагмента исчезал перед добавлением следующего. Нельзя приписывать этот дефект модели без проверки исходного ответа или маскировать вставкой пробелов: это повредит коду, URL и путям. Repair-pass отложить до воспроизведения склейки в исходном, не обработанном UI ответе модели.

### Реализация

1. Ввести единый pipeline ответа `raw model output → reasoning isolation → stream assembly → spacing quality gate → Markdown normalization → renderer`.
2. Сборщик ответа обязан сохранять границы и пробелы фрагментов без `trim()` каждого чанка. Добавить тесты на пробел в начале/конце чанка, переносы строк, Unicode, Markdown fences и inline-code.
3. Усилить Galen Core Prompt: естественные пробелы между словами, валидный GFM, пустая строка вокруг заголовков/списков/таблиц/кода, запрет отдавать повреждённый Markdown.
4. Добавить детектор аномальных склеек только для обычного текста вне fenced code, inline-code, URL, путей и идентификаторов. Признаки: неестественно длинная кириллическая последовательность, частые переходы между известными словоформами без пробела и повреждённая пунктуационная граница.
5. Если детектор сработал, выполнить один дешёвый repair-pass текущей моделью с `think:false`: исправить только пробелы и пунктуацию, полностью сохранить смысл и Markdown. Не запускать повторный проход для нормального ответа и никогда не чинить содержимое code spans/blocks.
6. Перед сохранением истории хранить нормализованный финальный ответ; raw/repair diagnostics держать только в debug-логе без reasoning.
7. Сделать renderer уровня готового продукта:
   - таблицы: скруглённый контейнер, чёткие заголовки, zebra rows, hover, горизонтальный scroll, корректная ширина колонок, кнопки «Копировать таблицу» и «CSV»;
   - код: язык, кнопка «Копировать», перенос строк on/off, горизонтальный scroll, сохранение отступов, нормальные цвета, отдельная кнопка запуска только для shell/PowerShell и только через permission flow;
   - заголовки, абзацы, списки, task lists, цитаты, разделители, inline-code, ссылки и изображения получают единый typography rhythm;
   - незаконченный streaming Markdown не должен мигать, ломать таблицу или проглатывать текст; сложный блок отображать после закрытия конструкции либо через стабильный incremental parser;
   - длинные строки, русские слова, emoji и мобильная/узкая ширина не разрушают layout.
8. HTML от модели не исполнять. Ссылки валидировать, внешние открытия оставлять через безопасный native handler.

### Критерий готовности

- В golden tests есть обычный русский ответ, намеренно склеенный ответ, таблица, несколько code fences, inline-code, URL, Windows path, список, цитата и незакрытый streaming fence.
- Склейки исправляются в прозе, но `camelCase`, `snake_case`, команды, URL и пути остаются побайтно неизменными.
- Визуально проверены таблицы и код на ширине 1440, 1024 и минимальной ширине приложения.
- Из каждой таблицы корректно копируется Markdown/CSV; из code block копируется исходный код без номеров строк.

## Обязательный этап: полноценная работа с консолью и готовыми файлами

### Пользовательский результат

Если пользователь пишет «создай файл/проект/скрипт/документ», нормальный итог — файл уже создан в выбранной рабочей папке, зависимости установлены при необходимости, проверки выполнены, а в чате показана карточка готового артефакта. Выводить полотно кода для ручного копирования можно только если пользователь прямо попросил код текстом или не дал доступ к рабочей папке.

### Инструменты агента

1. Не ограничиваться универсальным `run_terminal`. Добавить типизированные native tools:
   - `list_directory` и поиск файлов;
   - `read_file` с диапазонами и лимитами;
   - `write_file` с атомарной записью через временный файл;
   - `apply_patch` для точечных правок без перезаписи чужого кода;
   - `create_directory`, `copy_path`, `move_path`, `rename_path`;
   - `delete_path` только с отдельным опасным подтверждением и предпочтительно через корзину;
   - `run_terminal` для команд, установок, сборок и тестов;
   - `inspect_process` / `cancel_process` для долгих команд.
2. Терминальная сессия должна поддерживать явный `cwd`, PowerShell на Windows, stdout/stderr в реальном времени, exit code, timeout, отмену и ограниченный размер лога. Агент видит реальный результат каждого шага и не заявляет об успехе при ненулевом exit code.
3. Для многострочных файлов не строить хрупкие shell-команды с кавычками. Использовать `write_file`/`apply_patch`; terminal оставлять для выполнения и проверки.
4. После создания агент обязан выполнить подходящую проверку: открыть файл повторно, проверить существование/размер, затем lint/typecheck/test/build или безопасный smoke-run по типу проекта. Ошибку исправить в рамках agent loop, а не перекладывать ручную работу на пользователя.
5. Добавить artifact card в чат:
   - имя, тип, полный путь, размер и статус проверки;
   - «Открыть», «Показать в папке», «Копировать путь»;
   - для текстовых файлов — preview/diff; для изображений — thumbnail; для PDF — первая страница; для проекта — корневая папка и команды проверки;
   - карточка сохраняется в истории и после перезапуска остаётся рабочей, если файл существует.
6. Вести сворачиваемую ленту действий: «Изучаю папку», «Создаю файл», «Устанавливаю зависимости», «Проверяю сборку», «Готово». Внутренний chain-of-thought не показывать; показывать только проверяемые действия, команды и результаты.
7. Разрешения сделать гранулярными:
   - чтение внутри выбранной рабочей папки можно разрешить отдельно;
   - запись/изменение, установка зависимостей, запуск программ, сеть и удаление — отдельные scopes;
   - «Всегда разрешать» хранить по типу действия и workspace, а не как безусловное разрешение на весь компьютер;
   - любое удаление, выход за workspace, запуск с повышенными правами и системные изменения требуют отдельного подтверждения даже при обычном auto-allow, если пользователь явно не разрешил такой scope.
8. Защитить границу workspace: canonical path, запрет `..`/symlink escape, явное отображение внешнего пути, лимиты размера, таймауты, запрет чтения известных credential-файлов без отдельного подтверждения.
9. Agent loop должен уметь несколько tool calls подряд, корректно переживать отказ, timeout и ошибку, повторно читать изменённый файл и завершаться только подтверждённым результатом.

### Критерий готовности

- E2E: попросить создать рабочий PowerShell-скрипт и текстовый файл — оба появляются на диске, проходят проверку и открываются из artifact card без ручного копирования.
- E2E: создать маленький проект, установить зависимости, выполнить тест и показать готовую папку.
- E2E: изменить существующий файл через patch, не затронув соседние строки.
- E2E: отказ пользователя ничего не меняет; двойной клик не запускает действие дважды; timeout и ненулевой exit code видны как ошибка.
- Security tests: path traversal, symlink escape, удаление, запуск вне workspace и попытка прочитать credential-файл блокируются правильным permission scope.
- После перезапуска история действий не притворяется живой сессией, но artifact cards находят сохранённые файлы и честно показывают «файл перемещён/удалён», если путь больше не существует.

## Жёсткие блокеры

1. Папка `local-image-chat` находится на Windows-компьютере пользователя и недоступна этому Linux-раннеру, подключённой Library и GitHub. Без её файлов нельзя честно перенести обязательные workflow, model mapping, custom nodes и параметры запуска. Создавать другую реализацию с нуля запрещено планом.
2. Доступный GitHub connector не умеет создавать Actions Secrets. Приватный updater key нельзя коммитить или передавать через обычный файл. Для signed release нужен секрет `TAURI_SIGNING_PRIVATE_KEY` (и, если ключ защищён, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`) в настройках репозитория.
3. Windows-версия `v0.4.1` не содержит рабочего Tauri updater; её старый updater поддерживал автоматическую замену только AppImage. Поэтому полностью автоматический первый переход Windows `v0.4.1 → v0.5.0` технически невозможен задним числом. Первый Windows-переход должен быть установкой `v0.5.0` поверх `v0.4.1` с проверкой сохранения данных; последующие обновления будут автоматическими и подписанными.
